# Trace Web App + GitHub Integration — Implementation Prompt

You are building the **Trace web application and GitHub integration only**.

Do **NOT** build the Trace CLI package.  
Do **NOT** build the CLI's local repository monitoring functionality.  
Do **NOT** implement the CLI ingestion API beyond creating placeholder interfaces/types if absolutely necessary for future integration.

The deliverable is the complete Trace web application, its backend, database, authentication system, GitHub App integration, repository tracking system, activity ingestion from GitHub, dashboard, and daily report-generation system.

Two developers will work on this project simultaneously.

You MUST follow the sequential development plan below.

The plan has two critical requirements:

1. **The days are sequential.**
   Day N may depend only on work completed on Days 1 through N-1.

2. **Person A and Person B work independently within each day.**
   Person A's tasks must not require Person B's tasks from the same day to be completed.
   Person B's tasks must not require Person A's tasks from the same day to be completed.

Do not reorganize the plan into cross-dependent tasks.

==================================================
PRODUCT
==================================================

The application is called:

    Trace

Trace tracks software-development activity associated with GitHub repositories.

A user:

1. Creates a Trace account using username/password.
2. Logs into Trace.
3. Links their GitHub account.
4. Installs the Trace GitHub App / authorizes repository access.
5. Selects which repositories Trace should track.
6. Trace receives GitHub activity from those repositories.
7. Trace stores normalized activity data.
8. Trace provides dashboards and activity views.
9. Trace can generate a daily report summarizing the work performed across selected repositories.
10. The report is analyzed by an AI model and rendered into a LaTeX/PDF report.

The Trace CLI is being developed separately by another person/team.

Do not implement the CLI itself.

==================================================

    GitHub Contributor

Do not use GitHub identity as the primary Trace user identity.

==================================================
SEQUENTIAL DEPENDENCY RULE
==================================================

This rule is extremely important.

Do not begin Day N until Day N-1 is complete.

Within a day:

    Person A's work
    and
    Person B's work

must be independently executable.

If a person needs an API that the other person is building that same day, use the already-defined API contract and a mock.

Do not wait for the other developer's implementation.

Example:

BAD:

    Day 5 Person B:
        Build activity UI using Person A's activity API,
        which Person A is also creating on Day 5.

GOOD:

    Day 5:
        Person A:
            Builds webhook infrastructure.

        Person B:
            Builds activity UI against the already-defined
            activity data contract using mock data.

Then Day 7 integrates the real API.

==================================================
SHARED CONTRACT RULE
==================================================

Before implementing cross-boundary functionality, define stable contracts:

    TypeScript DTOs
    API schemas
    Database models
    Event schemas

Prefer shared packages for:

    packages/shared/

Use schema validation where appropriate.

Frontend and backend should be able to develop independently against these contracts.

==================================================
GITHUB SECURITY RULES
==================================================

Never:

- Ask users for GitHub personal access tokens
- Store unnecessary GitHub credentials
- Log GitHub private keys
- Skip webhook signature verification
- Trust repository IDs supplied blindly by webhook clients
- Trust frontend-provided user IDs
- Allow users to access another user's reports
- Allow users to manipulate another user's repository tracking configuration

Every repository-related request must be authorized against the authenticated Trace user.

==================================================
REPORT SECURITY
==================================================

Reports may contain private development information.

Ensure:

    User A cannot access User B's reports.

For shared repositories:

    Repository activity can include collaborators.

For future CLI activity:

    Local activity belongs to the Trace user/device
    that submitted it.

Do not expose local CLI activity merely because two users track the same repository.

Team/workspace sharing can be implemented later.

==================================================
FINAL DEFINITION OF DONE
==================================================

The web application is complete when a new user can:

1. Visit Trace.
2. Create a Trace account with username/password.
3. Log in.
4. Open GitHub settings.
5. Connect their GitHub account.
6. Install/authorize the Trace GitHub App.
7. See repositories available to Trace.
8. Select repositories to track.
9. See GitHub push/commit activity appear.
10. See collaborators' activity.
11. Filter activity by repository, contributor, and date.
12. Generate a daily report.
13. Have the activity summarized by an AI.
14. Have the structured summary converted into controlled LaTeX.
15. Download a PDF report.
16. Disconnect GitHub without destroying historical data.
17. Continue using their Trace account independently of GitHub.

The architecture must also be ready for a separately developed Trace CLI to later submit:

    working-tree changes
    staged changes
    untracked files
    local commits

without redesigning authentication, repositories, activity events, or report generation.
